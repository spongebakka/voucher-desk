# Voucher Desk: notes for Claude

The owner is a beginner and a restaurant supervisor, and they usually edit from their phone mid-shift. Keep replies short and plain-English, and end each change with what to test.

**Who uses the app:** only the host desk laptop, in a desktop browser. Nobody uses it on a phone. The owner talks to Claude Code from their phone, which is why sessions come from a phone, but **design and test for laptop screens only (about 1280–1440px wide)**. Don't spend effort on phone layouts. The existing small-screen CSS only needs to keep working so the owner can glance at the live site on their phone after a change.

**Workflow:** make changes on a branch and open a PR. Netlify posts a deploy-preview link on the PR, and the owner checks it there before saying "merge".

- The whole app is `index.html` (HTML, CSS and JS inline, no build step, no dependencies). Keep it that way.
- It is live on Netlify, deployed from `main`: https://voucher-desk.netlify.app/. A change only goes live once it's on `main`, and Netlify takes under a minute to update. When working on a branch, offer to merge it to `main` so the change can be tested.
- Data lives in the browser's localStorage under `voucherDesk.v1`. **Never rename that key or change the saved data's shape without migrating it**, or the host laptop loses its log.
- No real data goes in the repo (it's public): no staff names, codes or restaurant name. Those are entered in the app's Settings.
- No API for itison or Waiter Mate (the till, by OrderMate). The end of shift check compares the log with itison's per-deal lists (`…/hub/company/<id>/products/<deal id>/guestlists.csv`, columns Name, Voucher Code, PIN, Order Batch, Title, Price, Bought on, State, Redeemed on, Redeemed by). The helper add-on fetches them with the laptop's itison login, using the links saved in `settings.itisonExports`. Downloaded files can be used instead. A sister restaurant sells its own deals whose vouchers can be used here too. Their links go in `settings.itisonSisterExports`. Its name for labels is `settings.sisterName`, entered in Settings, never in the repo. From those lists, only vouchers redeemed by this restaurant's itison login count. That login is worked out from the "Redeemed by" column of this restaurant's own lists (the most common one), and the column is read in memory only. Sister rows redeemed by another login are `away`: never counted, and flagged if logged here. Downloaded files count as the sister's when their name starts with a sister deal number (itison names them `<deal>_N.csv`). History → "Check with itison" runs the same comparison (`compareNight`) for every night between History's From/To dates (default: the last 7 nights). These files hold customers' names and PINs: only code, title, state, redeemed time and PIN are read, in memory. A PIN is only saved when the host logs a missing voucher from the check ("Log it" / "Log all"), like any logged voucher. Names are never read. Never save the files or put them in the repo.
- A "night" runs 5am to 5am (`DAY_START_HOUR`).
- Flow: details (code, PIN, table, who) → redeem on itison → pick the deal itison shows (customers often only have a photo of the code, so the deal is only known after redeeming) → "Accepted" logs it with the itison step ticked, "Rejected" saves it with `status: 'rejected'` (left out of every total). The PIN is saved with each voucher (`pin`) because the restaurant wants a record of it. It's shown in the list, History and the CSV. Logged vouchers can be edited afterwards (pencil button in the list and History).
- One device: everyone brings vouchers to the host desk laptop, so the log lives there. Don't add a shared database unless that changes.
- **itison helper add-on** (`itison-helper/`, Chrome, loaded unpacked on the laptop). Voucher Desk opens itison at `?redeem-code=CODE#vd-code=CODE&vd-pin=PIN`. `itison.js` searches, opens the PIN box, fills the PIN, and the host presses Redeem. It reports `valid`, `redeemed`, `already`, `other` (expired…), `badpin`, `notfound` or `badcode` to the Voucher Desk tab that has `data-vd-pending` = that code (`background.js` and `desk.js`), then closes the itison tab. The page receives these as `postMessage({from:'vd-helper',…})`. itison has two result layouts: a big panel ("This voucher is valid for use" / "This voucher has been redeemed") and a short one ("Status: Redeemed"). A wrong PIN shows "Pin is incorrect". Bump `manifest.json` `version` with every change, and tell the owner to update (download main.zip, Replace the folder in Documents, press the reload arrow in chrome://extensions). There's no way to test against the real Hub from here: test with Playwright, the extension loaded, and stand-in itison pages built from the owner's photos.
- **Deals and itison matches:** `settings.deals` is `[{name, value}]`, where value is the till amount. `settings.itisonDeals` maps itison's deal text (e.g. "£50 voucher to spend on food & drinks") to a deal name. It's learned the first time the host picks a deal after a redemption, and can be edited in Settings → itison deal matches. Renaming a deal updates its matches, and removing a deal forgets them.
